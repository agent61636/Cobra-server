Redis is a tiny, fast, in-memory data store. On Cobra Island it has one job: carry messages between Paperless's web page and its background workers. "New scan in the inbox, please OCR it" goes into Redis; a worker picks it up, does the job, and posts the result back.

It lives in the gate pod on 127.0.0.1:6379, next to Paperless and Postgres. It has no web page and no login, which is fine because nothing outside the pod can reach it. Its folder /srv/gate/redis holds a snapshot of the queue so a restart doesn't forget work in progress.

Paperless's workers are run by a task system that needs a "broker" to pass jobs around. That broker is Redis: PAPERLESS_REDIS=redis://127.0.0.1:6379. Without it, the web page still opens, but nothing gets consumed, and scans pile up in the inbox.


        
CLAUDE-VIPEREvery good army needs a runner. Redis never sleeps, never complains, and never reads the messages it carries.

Do any other apps use this Redis?

        
No, only Paperless. RomM on the SGIN keeps its own small Redis inside its container (its /redis-data folder).

      

      

        
Does it need backups?

        
Not really. It only holds jobs in flight. The VM backup has it anyway.

      

    

  

  
PRO TIP: THE NAME

    
Redis stands for REmote DIctionary Server: a big table of keys and values, kept in memory. Paperless's queue is just a few of those keys.

IN MEMORY, MOSTLY

        
Redis keeps everything in RAM, which is why it's fast. Every so often it writes a snapshot to /data (our /srv/gate/redis), and reads it back when it starts. A queue of a few jobs is a few kilobytes.

      

      
WHY A QUEUE?

        
OCR on a 20-page scan can take a minute or more. If the web page did it itself, your browser would hang. With a queue, the page answers at once ("got it") and a worker grinds away in the background. You can upload ten files and keep browsing.

      

      
NO PASSWORD?

        
Redis here runs without a password. That's only safe because it listens inside the pod: the gate publishes nothing but nginx's 80 and 443, and the gate's own firewall drops everything else.

      

    

    

      
START ORDER

        
Paperless's Quadlet has Requires=postgres.service redis.service and After= the same. So systemd starts Redis before Paperless, and stopping Redis stops Paperless too.

      

      
VERSION PIN

        
The image is redis:7. Auto-updates bring 7.x fixes only. Paperless only needs a working broker, so there's no reason to chase the newest major.

      

      
IN THE BACKUP

        
It's in /srv/gate, so the nightly VM backup has it, but you'd never need to restore it. An empty Redis just means an empty to-do list.

PRO TIP: STUCK SCANS?

        
Files sitting in scans for more than a couple of minutes? Ping Redis first. If it answers, look at Paperless's log next.

      

      
PRO TIP: RESTART THE CREW

        
Restarting only Redis can leave Paperless's workers confused. Restart the three together, in order.

      

      
CODES

        GATE · podsvc
        systemctl --user restart redis paperless
      

    

    

      
THE SILENT STALL

        
Redis down, Paperless still shows its web page. Everything looks fine, but nothing gets consumed and the inbox fills up.Ping it. Uptime Kuma watches web pages, not Redis, so this one you check by hand.

      

      
THE EXPOSED RUNNER

        
A passwordless Redis reachable from the network is a classic break-in route.Never publish 6379. ss -tlnH on the gate must not show it.

      

      
THE OWNERSHIP TRAP

        
Like Postgres, Redis runs as its own user inside the container. A later chown -R podsvc: /srv/gate can leave it unable to write its snapshot.Don't re-run that chown. If Redis logs permission errors on /data, fix its folder the way you fixed Postgres's.

      

      
THE "FLUSH IT" URGE

        
Wiping Redis to "fix" Paperless throws away queued jobs, and their scans may already have left the inbox.Restart, don't flush.
